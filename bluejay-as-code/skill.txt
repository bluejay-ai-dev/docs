# Bluejay: testing and monitoring platform for conversational AI agents

You are a senior backend engineer integrating the Bluejay API. Think step-by-step: first understand the system, then plan the integration, then implement with minimal changes.

---

## Bluejay as Code overview

Bluejay as Code (BaC) is a pull/push workflow for managing Bluejay agent configuration as version-controlled files. Instead of configuring agents through the UI, you define everything in a YAML payload, commit it to source control, and push it to apply changes.

**Format:** Always use YAML. JSON payloads are deprecated on November 20th, 2026. If the project has a JSON payload file, move it to YAML: push it once if it has unpushed changes, pull the same root again, and replace the JSON file with the YAML one. The `bluejay_as_code_id` values stay the same.

The payload is simulation-centric: it describes a single simulation and all the objects that belong to it: its agent, the Digital Humans that participate in it, and the custom metrics used to evaluate it.

---

## The payload shape

Every BaC operation revolves around a single payload:

```yaml
agents:
- bluejay_as_code_id: ...
  # agent fields
simulations:
- bluejay_as_code_id: ...
  # simulation fields
digital_humans:
- bluejay_as_code_id: ...
  # digital human fields
custom_metrics:
- bluejay_as_code_id: ...
  # custom metric fields
```

**Constraints:**
- A pulled payload contains one agent and one simulation. A pushed payload can contain more. With more than one agent, list each simulation's `bluejay_as_code_id` in its agent's `simulations` list.
- `digital_humans` and `custom_metrics` are lists of any size (including empty).

**YAML rules:**
- Write multi-line text, such as a system prompt, as a `|` block.
- Quote any value YAML would read as something other than text, such as `'+15551234567'`, `'no'`, `'yes'`, `'on'`, `'off'`, or `'007'`. Unquoted, these become numbers or booleans.
- Do not use anchors or aliases (`&`, `*`). Bluejay rejects them with HTTP 400.

---

## The `bluejay_as_code_id`

Every entity in the payload has a `bluejay_as_code_id`. This is distinct from Bluejay's internal database ID. It is the stable handle used exclusively within the BaC system to identify and track objects across operations.

**Rules:**
- **You define it.** Pull populates the IDs of existing entities. For a new entity, generate a UUID once and hardcode it in your config file.
- **Keep it stable.** Changing a `bluejay_as_code_id` is equivalent to deleting the old entity and creating a new one.
- **It is BaC-scoped.** Bluejay uses it only for push/pull, never in simulations or the UI.

> You own the BaC IDs. This is intentional: it gives you full control over what Bluejay creates, updates, or re-links. Never auto-generate them at runtime.

## Endpoints

### Pull: GET /v1/bluejay-as-code/{root_type}/{root_id}

Exports a Bluejay configuration bundle as a BaC payload, with all `bluejay_as_code_id` values populated from Bluejay's database. The bundle is rooted at any of four entity types. Pick whichever entity is most natural to anchor on.

**Auth:** `X-API-Key` header

**Path parameters:**
| Name | Type | Description |
|------|------|-------------|
| root_type | string | One of `simulation`, `agent`, `digital-human`, `custom-metric`. |
| root_id | string | The Bluejay ID (or `bluejay_as_code_id` UUID) of the root entity. |

**Query parameters:**
| Name | Type | Description |
|------|------|-------------|
| format | string | Optional. The response is YAML by default. `json` returns JSON until it is deprecated. |

**Response:** Full BaC payload with `bluejay_as_code_id` populated on every entity.

**Usage pattern:** For most workflows, root on `simulation`. It pulls the simulation, its agent, every linked Digital Human, and every associated custom metric in one call. Pull once to bootstrap your config file, then commit the returned IDs. They are your source of truth going forward.

```python
import requests

def pull_bluejay_as_code(root_id: str, api_key: str, root_type: str = "simulation") -> str:
    # root_type can also be "agent", "digital-human", or "custom-metric"
    url = f"https://api.getbluejay.ai/v1/bluejay-as-code/{root_type}/{root_id}"
    headers = {"X-API-Key": api_key}
    response = requests.get(url, headers=headers, params={"format": "yaml"})
    response.raise_for_status()
    return response.text  # write this to the payload file as is
```

### Push: POST /v1/bluejay-as-code

Applies a BaC payload to Bluejay. Each entity is matched by `bluejay_as_code_id` and created, updated, or left untouched depending on whether it exists and whether its fields have changed. The endpoint is the same regardless of which root_type was used to pull the bundle.

**Auth:** `X-API-Key` header
**Content-Type:** application/yaml (with any other Content-Type the body is read as JSON, so a YAML body fails)
**Body:** the YAML file contents, sent as raw bytes. With curl use `--data-binary @file.yaml`, never `--data`, which strips line breaks.
**Response:** always JSON.

**Query parameters:**
| Name | Type | Description |
|------|------|-------------|
| dry_run | boolean | Optional. `true` returns the plan with `dry_run: true` and writes nothing. |
| prune | boolean | Optional. `true` deletes entities the push leaves with no links at all: a Digital Human in no simulation, a custom metric on no agent, a simulation removed from its agent's `simulations` list. Default `false`: nothing is deleted. |

**Diffing behavior:**
| Scenario | Result |
|----------|--------|
| `bluejay_as_code_id` not found in Bluejay | Entity is created |
| Found, fields unchanged | No-op (`Unchanged ...`) |
| Found, fields changed | Entity is updated |
| Digital Human absent from payload | Detached from simulation (not deleted) |
| Digital Human exists on another simulation | Re-linked, not duplicated |
| Entity left with no links, and `prune=true` | Entity is deleted. Without `prune`, nothing is deleted. |

**Response:**
| Field | Type | Description |
|-------|------|-------------|
| valid | boolean | True iff the payload passed validation. |
| errors | EntityValidationError[] | Per-entity validation errors. Empty when `valid` is true. |
| dry_run | boolean | True when the request was a dry run and nothing was written. |
| actions | string[] | One line per entity. Each starts with `Created`, `Updated`, `Unchanged`, `Linked`, `Unlinked`, `Deleted` (push with `prune=true`), or `Would delete` (dry run with `prune=true`). |
| simulation_id | integer \| null | Resolved Bluejay ID of the simulation in the bundle (when present). |

```json
{
  "valid": true,
  "errors": [],
  "dry_run": true,
  "actions": [
    "Updated agent 'Front Desk Scheduler'",
    "Unchanged simulation 'Scheduling Coverage'",
    "Created digital human 'Eleanor Pham'",
    "Would delete digital human 'Maria Alvarez'"
  ],
  "simulation_id": 1284
}
```

**Status codes:**
| Code | Meaning |
|------|---------|
| 200 | Applied, or planned when `dry_run=true`. |
| 400 | The YAML cannot be read, a link points to an entity that is in neither the payload nor Bluejay, or a new simulation does not have exactly one agent. |
| 422 | The payload failed validation. Same body as a 200: `valid` is `false` and `errors` lists the problems. `curl -f` and `raise_for_status()` fail on it, so a CI step fails on its own. |

**Rollback:** if a step fails after writes began, Bluejay rolls the push back. Entities it created are deleted, entities it updated are restored, links are restored. The error body is:

```json
{
  "detail": {
    "error": "...",
    "applied": ["Created digital human 'Eleanor Pham'"],
    "rolled_back": ["Created digital human 'Eleanor Pham'"],
    "rollback_failed": []
  }
}
```

`rollback_failed` lists anything that could not be restored. Surface it to the user when it is not empty.

**Always plan first.** Before any push that writes, call the endpoint with `dry_run=true`, show the user the `actions` list, and push only after they confirm. Never push with `prune=true` without showing the `Would delete` lines first.

```python
import requests

BASE_URL = "https://api.getbluejay.ai/v1/bluejay-as-code"


def plan_bluejay_as_code(payload_yaml: str, api_key: str, prune: bool = False) -> list[str]:
    # Returns the actions a push would perform. Writes nothing.
    return _post(payload_yaml, api_key, dry_run=True, prune=prune)["actions"]


def push_bluejay_as_code(payload_yaml: str, api_key: str, prune: bool = False) -> dict:
    return _post(payload_yaml, api_key, dry_run=False, prune=prune)


def _post(payload_yaml: str, api_key: str, dry_run: bool, prune: bool) -> dict:
    headers = {"X-API-Key": api_key, "Content-Type": "application/yaml"}
    params = {"dry_run": str(dry_run).lower(), "prune": str(prune).lower()}
    response = requests.post(BASE_URL, headers=headers, params=params, data=payload_yaml.encode("utf-8"))
    if response.status_code == 422:
        raise ValueError(f"Push failed validation: {response.json()['errors']}")
    if response.status_code >= 400:
        detail = response.json().get("detail", response.text)
        raise RuntimeError(f"Push failed: {detail}")  # detail may hold applied / rolled_back / rollback_failed
    return response.json()
```

**CI pattern:** run the plan on the pull request and the push on merge. Check the status code, not `valid`.

```bash
# Pull request: plan only, nothing is written
curl --fail-with-body "https://api.getbluejay.ai/v1/bluejay-as-code?dry_run=true" \
  -H "X-API-Key: $BLUEJAY_API_KEY" -H "Content-Type: application/yaml" \
  --data-binary @simulation.yaml

# Merge: push
curl --fail-with-body https://api.getbluejay.ai/v1/bluejay-as-code \
  -H "X-API-Key: $BLUEJAY_API_KEY" -H "Content-Type: application/yaml" \
  --data-binary @simulation.yaml
```

`--fail-with-body` needs curl 7.76 or later. Older curl: use `-f`, which hides the body.

## MCP tools

When the Bluejay MCP server is connected, prefer its tools over hand-written HTTP calls:

| Tool | Arguments | Does |
|------|-----------|------|
| `pull_bluejay_as_code` | `root_type`, `root_id`, `format` | Pull the payload for one root entity. |
| `plan_bluejay_as_code` | `payload` | Return the plan. Writes nothing. |
| `push_bluejay_as_code` | `payload`, `prune` | Push the payload. `prune=true` deletes entities left with no links. |

Same rule as the HTTP API: call `plan_bluejay_as_code`, show the user the plan, then call `push_bluejay_as_code` only after they confirm.

## Full end-to-end example

```python
import uuid
import requests
import yaml  # PyYAML

BASE_URL = "https://api.getbluejay.ai/v1"
API_KEY  = "your-api-key"
SIM_ID   = "your-simulation-uuid"

# 1. Pull current config as YAML — anchored on the simulation
pulled = requests.get(
    f"{BASE_URL}/bluejay-as-code/simulation/{SIM_ID}",
    headers={"X-API-Key": API_KEY},
    params={"format": "yaml"},
).text
payload = yaml.safe_load(pulled)

# 2. Edit — update the agent system prompt
payload["agents"][0]["system_prompt"] = "You are a helpful support agent. Always greet the customer by name."

# 3. Add a new digital human
#    Generate a UUID once, then hardcode it in your config — never regenerate at runtime
payload["digital_humans"].append({
    "bluejay_as_code_id": str(uuid.uuid4()),
    "human_name": "Frustrated Caller",
    "description": "A customer who has been on hold for 20 minutes and wants a quick resolution.",
    "language": "en",
    "simulations": [payload["simulations"][0]["bluejay_as_code_id"]],
})

# 4. Plan — dry run, writes nothing. Show these lines to the user before pushing.
#    In a real project, edit the committed YAML file instead and push its contents.
body = yaml.safe_dump(payload, sort_keys=False, allow_unicode=True)
headers = {"X-API-Key": API_KEY, "Content-Type": "application/yaml"}

plan = requests.post(
    f"{BASE_URL}/bluejay-as-code",
    headers=headers,
    params={"dry_run": "true"},
    data=body.encode("utf-8"),
)
plan.raise_for_status()  # 422 means the payload failed validation; the body has `errors`
for action in plan.json()["actions"]:
    print(action)

# 5. Push — only after the user has confirmed the plan.
#    Single unified endpoint regardless of which root_type you pulled from.
result = requests.post(
    f"{BASE_URL}/bluejay-as-code",
    headers=headers,
    data=body.encode("utf-8"),
)
result.raise_for_status()
result = result.json()

# result["simulation_id"] is the resolved Bluejay ID of the simulation in the bundle
```

## Integration constraints

- **Minimal changes:** only add or modify files required for this integration.
- **Match existing patterns:** follow the project's naming conventions, file structure, and error-handling style.
- **Stable IDs:** `bluejay_as_code_id` values must be hardcoded UUIDs in your config file, never generated dynamically at push time.
- **Plan first:** run a dry run (`dry_run=true` or `plan_bluejay_as_code`) and show the user the `actions` list before any push that writes. Never push with `prune=true` without showing the `Would delete` lines.
- **Check the status code:** a push that fails validation returns HTTP 422 with `valid: false` and `errors`. Surface `errors` to the user. `valid` in a 200 body is always `true`.
- **Handle rollback:** on any other 4xx/5xx, read `detail.applied`, `detail.rolled_back`, and `detail.rollback_failed`. Tell the user about anything in `rollback_failed`.
