A Digital Human is a simulated customer that can call, text, or email your agent. Each one has a goal, and Bluejay grades whether your agent handled it.

You can also create Digital Humans in the app from a CSV upload or from an IVR Flow.

## Persona

The **Persona** tab says who the caller is, what they want, and what counts as a pass. These settings decide what each conversation is about and how Bluejay grades it.

| Setting | API field | API default | Effect |
|---|---|---|---|
| Description / Intent | `intent` | None | What the caller wants, in one or two sentences. |
| Success Criteria | <Code>success_criteria</Code> | None | The pass or fail condition, as one or two agent outcomes the transcript can show. |
| Personality | <Code>role_description</Code> | None | Who the caller is, in one short line, for example "retiree on a family plan". |
| Scripted Responses | <Code>scripted_responses</Code> | None | Fixed replies to specific agent lines. See [Scripted responses](#scripted-responses). |
| Tool Adherence | <Code>expected_tool_calls</Code> | None | The tool calls the agent must make. |
| API only | `num_runs` | 1 | How many times this Digital Human runs in each simulation run. |

Keep agent behavior and "if X, do Y" rules out of the intent. The model treats them only as suggestions, so use the fields in [Make runs repeatable](#make-runs-repeatable) instead.

## Behavior

The **Behavior** tab sets how the caller sounds and acts: their voice, the line quality, how much they talk, and how long they wait for the agent. Use these settings to test whether your agent copes with harder callers, for example a fast talker on a bad connection.

| Setting | API field | Values | API default |
|---|---|---|---|
| Voice | `language`<br/>`accent`<br/>`gender` | Valid combinations from <Code>get_voice_options</Code> | `en` |
| Voice Speed | `voice_speed` | `slowest`, `slow`, `normal`, `fast`, `fastest` | `normal` |
| Background Noise | <Code>background_noise</Code> | `none`, a preset, or `custom`. `custom` needs <Code>custom_background_noise_url</Code>. | `none` |
| Background Noise Volume | <Code>background_noise_volume</Code> | 0 to 1 | 0.8 |
| Audio Quality | <Code>audio_quality</Code> | `high`, `medium`, `low`, `horrible` | `high` |
| Dropouts | <Code>connection_quality</Code> | `none`, `low`, `medium`, `high` | `none` |
| Verbosity | `verbosity` | `low`, `medium`, `high` | `medium` |
| Fluency | `fluency` | `beginner`, `intermediate`, `native` | `native` |
| Creativity | `creativity` | 0 to 2 | 0.7 |
| Patience (seconds) | <Code>endpointing_delay</Code> | Seconds to wait before a reply | 1.5 |
| No Response Timeout (seconds) | <Code>silence_timeout</Code> | 15 seconds or more | None |
| Interruptions | `interruptions` | None, Probabilistic, Keywords, Contextual | None |
| Speaks First | <Code>speaks_first_config</Code> | Who speaks first, and the opening message | The Digital Human speaks first. Some voice platform connections start with the agent. |

There is no emotion setting. To make the caller angry, rushed, or confused, write that attitude into **Personality** (`role_description`).

## Traits

A trait is a fact that the caller knows and says when the agent asks, for example a member ID or date of birth. Use a trait when the value must be the same on each run. If you write the value in the intent instead, the caller can say a different value on each run.

A trait belongs to one agent. Define it on the **Customer Traits** page, then set its value on each Digital Human.

To also send a trait as a SIP header on the call, set `is_sip_header` to `true`. The header name is the trait name with an `X-` prefix.

When you change a trait, select **Update Existing Digital Humans** to apply the change to all Digital Humans of the agent. Otherwise only new Digital Humans get the change.

## Tools

The **Tools** tab controls what the Digital Human can do besides talk, for example end the call, stay silent, or press keypad keys.

| Setting | API field | API default | Effect |
|---|---|---|---|
| Allow End Call Tool | <Code>allow_end_call_tool</Code> | `true` | The Digital Human can end the call. |
| End Conversation (On Trigger Phrases) | <Code>hangup_phrases</Code> | None | Agent phrases that end the call. |
| Allow Silence Tool | <Code>allow_silence_tool</Code> | `true` | The Digital Human can stay silent. |
| Allow DTMF Tool | <Code>allow_dtmf_tool</Code> | `true` | The Digital Human can send keypad tones. |
| Default Number Submission Mode | <Code>default_dtmf_or_voiced</Code> | `voiced` | Used when the agent does not say how to enter a number. |

## Connection

The **Connection** tab sets the phone number the Digital Human uses and how it gets through to your agent.

| Setting | API field | API default | Effect |
|---|---|---|---|
| Phone number | <Code>phone_number</Code> | None | The number of the Digital Human. It must be a number that your organization owns. |
| Extension | `extension` | None | Keys to send as DTMF after the call connects to an inbound agent, for example `1,2`. A comma adds a short pause. |
| Always On | <Code>always_on_mode</Code> | `false` | The Digital Human answers calls on its phone number. |

Each Digital Human calls or texts from its own number, which you set in **Phone number** above. It must be a number that your organization owns.

Each number belongs to the workspace you bought it in. The app lists only the current workspace's numbers, so buy numbers in the workspace where your Digital Humans live.

To list a workspace's numbers, use [Get Phone Numbers](/api-reference/endpoint/phone-numbers). You can also ask your AI assistant through the [workspace MCP tools](/mcp/workspace-tools#phone-numbers), which can list, buy, and release numbers.

## Scripted responses

A scripted response makes a reply the same on each run. Each item pairs an agent line with a response.

| Field | Values | Notes |
|---|---|---|
| <Code>match_phrase</Code> | string | A line the agent says, for example "Can I have your account number?". A description of agent behavior never matches. |
| `match_type` | `exact`, `context` | `context` matches lines with the same meaning. |
| <Code>response_type</Code> | `phrase`, `dtmf`, `silence`, `audio` | |
| <Code>response_value</Code> | string | Required for `phrase` and `dtmf`. Do not set it for `audio`. `audio` uses <Code>scripted_response_audio_snippet_url</Code>. |
| <Code>occurrence_mode</Code> | `always`, `first_n` | `first_n` needs <Code>occurrence_n</Code>. |

If `scripted_responses_ordered` is `true`, the responses run in list order and each fires once.

## Personalities

A Personality configures how Digital Humans behave. Use Personalities when you want to test the same goal with different callers.

When you select Personalities on a simulation, each Digital Human in the run calls once as itself and once for each Personality.

Start from a preset, for example **Fast talker**, and change only the fields you need. A Personality changes only the fields that you set on it, for example the **Personality** text (`role_description`), voice, background noise, or the [behavior fields](#behavior). All other fields come from the Digital Human. A Personality never changes the intent or the success criteria, so each call still tests the same goal.

The simulation saves its Personality selection, so the next run uses the same set.

### Limits

- A [customer journey](/test/simulation-types/customer-journeys) does not run once for each Personality.
- A change to a Personality applies to future runs only.
- If you delete a Personality, Bluejay removes it from each simulation that selects it. Past conversations show "Personality no longer exists".

## Communities

A Community is a saved group of Digital Humans that you can reuse in any simulation, which makes it a test suite for an agent or a flow.

Group the Digital Humans that cover one agent or one flow into a Community. Select the Community when you create a simulation, so each agent version runs against the same callers and the results compare directly.

When an agent fails on a real conversation, create a Digital Human that recreates the failure and add it to the Community. The next run then tests for that failure again.

## Write a good Digital Human

- Test one goal in each Digital Human. Booking, rescheduling, and cancelling are three Digital Humans.
- Write **Description / Intent** as what the caller wants. If you write "correctly" or "successfully", that text describes the agent, so move it to **Success Criteria**.
- Write **Success Criteria** as an agent outcome that the transcript can show.
- Put grading that applies to every call in a [custom metric](/test/metrics), not in **Success Criteria**.

| Setting | Do | Do not |
|---|---|---|
| Description / Intent | "You want to move your dentist appointment to next week." | "Make sure the agent correctly reschedules. If it asks for your date of birth, say March 3, 1980." |
| Success Criteria | "The agent moved the appointment and confirmed the new date." | "The caller gives the date of birth and stays polite." |

### Make runs repeatable

An "if the agent says X, the caller does Y" rule in the intent is only a suggestion to the model, so the caller may not follow it on every run. Move it to the setting that fixes it:

| Need | Setting |
|---|---|
| A fixed value, for example a date of birth | **Traits** (`traits`) |
| A fixed line, keypad entry, or pause | **Scripted Responses** (<Code>scripted_responses</Code>) |
| A fixed opening line | **Speaks First** (<Code>speaks_first_config</Code>) |
| The same call on each run | **Creativity** (`creativity`) from 0.0 to 0.3 |

Before you create a batch, create one Digital Human, run it, and read the transcript. Bluejay accepts a configuration that has no effect, for example a scripted response that never matches, so the transcript is where you see whether each setting worked.

To test a phone tree, draw an IVR Flow on the **Scenario Builder** page and run it with the [IVR Flow](/test/simulation-types/ivr-flow) simulation type.
