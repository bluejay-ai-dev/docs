## Metric types

| Type | How it scores |
|---|---|
| LLM as a Judge | An LLM scores the conversation against your prompt. |
| Composite | Combines the results of other metrics into one score or label. |
| Tool Call | Passes when the agent called the tools you name. |
| Phrase Match | Checks whether specific words were said. |
| Transfer Landed | Passes when the Digital Human you choose answers a transfer from the agent in time. The default limit is 180 seconds, and the maximum is 900. |

Only LLM as a Judge uses a prompt, and its response type sets the shape of its result. Tool Call, Phrase Match, and Transfer Landed always return Pass/Fail.

## Response types

Choose the response type that matches the question your prompt asks:

| Response type | Example |
|---|---|
| Pass/Fail | Did the agent verify identity before it shared account details? |
| Yes/No | Did the customer ask for a human? |
| Number | Rate the clarity of the explanation from 1 to 5. |
| Text | Summarize the objections the customer raised. |
| Categorical | Classify the call as `resolved`, `escalated`, or `unresolved`. |
| Structured JSON | Return `identity_verified` (boolean) and `flags` (string array). |

## Prompting guide

An LLM as a Judge metric sends your prompt and the conversation to the judge, the AI model that scores the metric. A vague prompt can make the judge pass one call and fail an almost identical call. The rules below help it give the same verdict on similar calls.

### Rules for all response types

- Write criteria that a reader can answer from the transcript or the audio.
- Test one thing per metric. If two results matter independently, write two metrics.
- Replace words such as "good", "appropriate", or "well" with behavior that you can see in the transcript.
- Write what the metric verifies, not what the agent must do. Agent instructions go in the agent prompt.

### Prompts by response type

<Tabs>
  <Tab title="Pass/Fail">
    State the pass condition and the fail condition. Give one example of each.

    ```
    The metric passes if the agent asked for at least two of: full name,
    date of birth, last four digits of the card, or billing ZIP code,
    BEFORE it shared any account details.

    The metric fails if the agent asked for fewer than two, or shared
    account details first.

    Example pass: agent asked for date of birth and last four, then
    quoted the balance.
    Example fail: agent quoted the balance after it confirmed only the name.
    ```

    Do not write "Did the agent verify and help the customer well?" That prompt tests two behaviors and uses an undefined word.
  </Tab>
  <Tab title="Number">
    Define each level on the scale. Use five levels or fewer. With no definitions, the judge can give a 4 on one call and an 8 on an almost identical call.

    ```
    Rate the clarity of the agent's explanation from 1 to 5.

    1 = Confusing. The customer cannot act on the explanation.
    2 = Partial. The agent used key terms without a definition.
    3 = Adequate. The customer can act, but must guess some steps.
    4 = Clear. The agent named the steps in order.
    5 = Exceptional. The agent named the steps in order and confirmed
        them with the customer.
    ```
  </Tab>
  <Tab title="Text">
    Set a fixed structure and a word limit, so that you can compare outputs across calls. Ask for observations, not opinions.

    ```
    Summarize how the agent handled customer objections.

    Include:
    1. Each objection the customer raised, in order.
    2. The agent's response to each, quoted briefly.
    3. Whether the response resolved the objection (yes, partial, no).

    Keep the response under 120 words.
    ```
  </Tab>
  <Tab title="Categorical">
    Define the evidence for each label. Give one rule for calls that match more than one label. Use seven labels or fewer, and put rare cases in an `other` label.

    ```
    Classify this call into exactly one category.

    - new_order: The customer places an order they did not place before.
    - modify_order: The customer changes or adds to an existing order.
    - order_status: The customer asks where an existing order is.
    - complaint: The customer reports a problem with an order or the service.
    - general_inquiry: The customer asks about hours, locations, menu,
      or prices and does not place or change an order.

    If two categories apply, select the category that used the most call time.
    ```
  </Tab>
  <Tab title="Structured JSON">
    Give each key a type and a definition, and tell the judge to return only the object. Put the same shape in the metric's **JSON Schema** field (`json_schema` in the API), because the judge output must match it.

    ```
    Return a JSON object with exactly these keys:

    - identity_verified (boolean): true if the agent verified identity with
      at least two factors before it shared account details.
    - disclosure_read (boolean): true if the agent read the recording
      disclosure in the first 15 seconds.
    - flags (string[]): one short sentence for each compliance issue.
      Empty array if there are none.

    Return only the JSON object.
    ```
  </Tab>
</Tabs>

### Dynamic variables

To put a call-specific value into a metric, such as the customer's name, use a dynamic variable. Write `{{key}}` in `prompt` or `scoring_guidance`. Before the judge runs, Bluejay replaces each `{{key}}` with the value of `key` in the conversation `metadata`.

```
Prompt:    Did the agent confirm the account ending in {{account_last_four}}
           for {{customer_name}}?
metadata:  { "customer_name": "Sarah", "account_last_four": "4821" }
Judge sees: Did the agent confirm the account ending in 4821 for Sarah?
```

Each top-level key in the conversation `metadata` is a variable. If you send conversations with [`/v1/evaluate`](/api-reference/endpoint/evaluate), put the keys in its `metadata` object. If a voice platform sends your calls to Bluejay, the integration page for that platform says if its call metadata is included.

Example `/v1/evaluate` request:

```json
{
  "agent_id": "your-agent-id",
  "transcript": [...],
  "metadata": {
    "product_name": "Business Pro",
    "monthly_price": "149"
  }
}
```

#### Rules

- A key contains only letters, digits, and underscores. `{{customer name}}` and `{{order.id}}` are not replaced.
- Keys are case-sensitive.

<Warning>
If a key is missing, the judge sees `undefined` in the prompt and can give a wrong verdict. Make sure each key in the prompt is in the `metadata` of every conversation that the metric evaluates.
</Warning>

## Composite metrics

Use a composite metric to roll several metrics into one score or label. It cannot use another composite or conditional metric. For example, combine a clarity score and a Pass/Fail check into one Scheduling Quality score. A composite metric reads results that the other metrics already produced, so it makes no LLM call.

To get a number, write a formula. To get a label, write rules. The [composite metric example](/key-concepts/bluejay-as-code/cookbook#composite-metrics) shows both.

## Conditional metrics

Use a conditional metric when a rule applies only to some conversations. It cannot use another composite or conditional metric. For example, check the refund policy wording only when the agent called the refund tool. On other conversations, the result is Not Applicable. A condition can check that:

- The conversation reached a node of the agent [Workflow](/test/simulations/create#connect-your-agent). To find node IDs, use [Get Workflow Summary](/api-reference/endpoint/get-workflow-summary).
- The agent called a given tool.
- Another metric has a given result, for example Fail.

Join conditions with "and" or "or". The [conditional metric example](/key-concepts/bluejay-as-code/cookbook#conditional-metrics) shows the YAML.

## Tool calls, events, and metadata

A transcript does not show which tools your agent called. To grade tool calls, send them to Bluejay with the conversation. You can send events and metadata in the same way.

### Send tool calls

<Tabs>
  <Tab title="Simulations">
    Bluejay sends an `X-Simulation-Result-Id` with each simulated call, so that your agent can tell Bluejay which call its tool calls belong to. Your agent reads the ID, records its tool calls during the call, and sends them with the ID after the call ends.

    | Connection | Where the ID arrives |
    |------------|----------------------|
    | [SIP](/integrations/sip) | A custom header on the SIP INVITE. |
    | [WebSocket](/integrations/websockets) | A header on the WebSocket upgrade request. |

    The phone network usually drops custom headers, so a Phone connection cannot pass the ID. Use SIP for phone agents. If you use a voice platform or framework, its integration page says where the ID arrives.

    After the call ends, send the data to [`POST /v1/update-simulation-result`](/api-reference/endpoint/update-simulation-result):

    ```json
    {
      "simulation_result_id": "1234",
      "tool_calls": [
        {
          "name": "transfer_funds",
          "parameters": { "from": "12345", "to": "67890", "amount": 500 },
          "output": { "transaction_id": "txn_abc123", "status": "completed" },
          "start_offset_ms": 120000
        }
      ],
      "events": [
        { "title": "Customer verified", "start_offset_ms": 30000, "tags": ["verification"] }
      ],
      "metadata": { "resolution_status": "resolved" }
    }
    ```

    Some integrations collect tool calls without this API call. The integration page for your platform says if it does.
  </Tab>
  <Tab title="Production">
    Put `tool_calls`, `events`, and `metadata` in the same [`POST /v1/evaluate`](/api-reference/endpoint/evaluate) request as the transcript or recording, because you cannot add them later.

    ```json
    {
      "agent_id": "123",
      "start_time_utc": "2026-07-16T18:00:00Z",
      "participants": [
        { "role": "AGENT", "spoke_first": true },
        { "role": "USER", "spoke_first": false }
      ],
      "recording_url": "https://storage.example.com/call.mp3",
      "tool_calls": [
        {
          "name": "check_order_status",
          "start_offset_ms": 2000,
          "description": "Look up order status by order ID",
          "parameters": { "order_id": "ORD-2024-001" },
          "output": { "status": "in_transit" }
        }
      ],
      "metadata": { "customer_tier": "premium" }
    }
    ```
  </Tab>
</Tabs>

### Tool call fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | Yes | The tool name. |
| `start_offset_ms` | integer | Yes | Milliseconds from the start of the conversation. |
| `description` | string | No | What the tool does. Custom Metrics read it. |
| `parameters` | object | No | The input to the tool. |
| `output` | any | No | The value the tool returned. |

### Event fields

An event marks a moment in the conversation, for example an escalation or a hold.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `title` | string | Yes | The event name. |
| `start_offset_ms` | integer | Yes | Milliseconds from the start of the conversation. |
| `end_offset_ms` | integer | No | When the event ended. |
| `description` | string | No | Details of the event. |
| `tags` | string[] | No | Tags for the event. |
| `metadata` | object | No | Extra data for the event. |

### Metadata

`metadata` is a free-form JSON object for the whole conversation. Use it to give your custom metrics call-specific values: Bluejay puts each key into the matching `{{placeholder}}` in a metric. See [dynamic variables](/improve/custom-metrics#dynamic-variables).

### Build a lab

A lab pairs one or more custom metrics with a sample of conversations from an agent or a simulation run. Bluejay tunes the metric on this sample, so the tuned metric is only as good as the sample. Select 20 to 50 conversations for each metric, and include clear passes, clear fails, and unclear cases.

![The Lab tab on the Metrics page with the Create Lab button](/images/metrics-lab-landing.png)

![The Create Lab dialog with the name, metrics, and conversations steps](/images/metrics-lab-create-dialog.png)

### Label the conversations

Your label is the human verdict, and the metric's result is the AI verdict. The alignment score shows how often the two agree. To save time, label in bulk when many rows share the same verdict.

![The Annotate tab with AI and Human columns](/images/metrics-lab-annotate-table.png)

<Note>
Label every conversation before you read the alignment score. The score compares only rows that have a human verdict.
</Note>

### Improve the metric

Click **Run** to test the metric on the selected conversations, and **Improve** for Bluejay to create a new prompt revision to test.

![The Optimize tab with a prompt diff, Improve, and Published status](/images/metrics-lab-optimize-table.png)

### Keep the lab current

When production shows new cases, add them to the lab, label them, and publish again if alignment improves.
