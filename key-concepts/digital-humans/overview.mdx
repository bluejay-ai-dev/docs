## Create a Digital Human

To add Digital Humans to a simulation, write them one at a time, generate them from the agent context, or [upload a CSV](/key-concepts/digital-humans/csv-upload). To use the same set again, group them in a [Community](/key-concepts/communities/overview).

The sections below list each field by the tab of the Digital Human editor where you set it. The API and the `create_digital_humans` MCP tool use the same field names.

## Persona

<ParamField path="intent" type="string">
  The scenario, in one or two sentences: what the caller wants. Do not put agent behavior or "if X, do Y" rules here. Leave it empty when `enriched_playback` is set. The UI label is **Description / Intent**.
</ParamField>
<ParamField path="success_criteria" type="string">
  The pass or fail condition for this test: one or two outcomes of the agent that the transcript can show. Put a scored checklist in a [Custom Metric](/key-concepts/custom-metrics/overview).
</ParamField>
<ParamField path="role_description" type="string">
  Who the caller is, in one short line, for example "retiree on a family plan". Identity and attitude only. The UI label is **Personality**.
</ParamField>
<ParamField path="scripted_responses" type="object[]">
  Fixed replies to specific agent lines. See [Scripted responses](#scripted-responses).
</ParamField>
<ParamField path="expected_tool_calls" type="object[]">
  Tool calls the agent must make. Each item has `name`, and optional `parameters` and `output`. The UI label is **Tool Adherence**.
</ParamField>
<ParamField path="name" type="string">
  The caller name. `test_name` is a separate label for the Digital Human.
</ParamField>
<ParamField path="num_runs" type="integer" default="1">
  How many times this Digital Human runs in each simulation run. Minimum 1.
</ParamField>

There is no emotion field. Write the attitude into `role_description`.

To run each Digital Human with other behavior values in the same run, use [Personalities](/key-concepts/digital-humans/personalities).

## Traits

A trait is a case fact that the caller knows and can say when the agent asks, for example a member ID, date of birth, or order number. A fixed trait value makes the call repeatable. If you write the value in `intent`, the model can say a different value on each run.

Do not put agent-side data in a trait, for example CRM contents, expected tool arguments, or notes for the grader. Use `expected_tool_calls`, `success_criteria`, or a [Custom Metric](/key-concepts/custom-metrics/overview) for those.

### Create a trait

A trait belongs to one agent.

1. Open the **Customer Traits** page.
2. Select the agent.
3. Click **Create**.
4. Enter the trait name, the data type, and an optional default value.
5. Click **Create Trait**.

With the API, send `POST /v1/create-customer-trait` with `agent_id`, `name`, `data_type`, and `default_value`.

| Field | Values |
|---|---|
| Name | The name the agent asks for, for example `member_id`. Use the same name across the test suite. |
| Data type | `BOOLEAN`, `STRING`, `DATE` (ISO 8601), or `NUMBER` |
| Default value | The value that new Digital Humans get. Optional. |

### Set a value on a Digital Human

On the **Traits** tab of a Digital Human, set a value for each trait. With the API, set `traits` on the Digital Human. Each item has `trait_name`, `trait_data_type`, and `value`.

If `is_sip_header` is `true`, Bluejay also sends the trait as a SIP header on the call. The header name is the trait name with an `X-` prefix.

### Change a trait

When you save a change, select one option:

- **Future Digital Humans**: only new Digital Humans get the change.
- **Update Existing Digital Humans**: all Digital Humans of the agent get the new name, type, and value.

With the API, send `PUT /v1/update-customer-trait/{trait_id}`. Set `sync_existing` to `true` to update existing Digital Humans.

## Tools

| Field | UI label | Default | Effect |
|---|---|---|---|
| `allow_end_call_tool` | Allow End Call Tool | `true` | The Digital Human can end the call. |
| `hangup_phrases` | End Conversation (On Trigger Phrases) | None | Agent phrases that end the call. |
| `hangup_instructions` | Override End Conversation Instructions | `default` | Any value other than `default` replaces the built-in hangup behavior. |
| `allow_silence_tool` | Allow Silence Tool | `true` | The Digital Human can stay silent. |
| `silence_tool_instructions` | Silence Tool Instructions | `default` | Custom guidance for when to stay silent. |
| `allow_dtmf_tool` | Allow DTMF Tool | `true` | The Digital Human can send keypad tones. |
| `default_dtmf_or_voiced` | Default Number Submission Mode | `voiced` | Used when the agent does not say how to enter a number. |
| `outbound_text_number` | Send SMS | Agent number | The number the Digital Human texts during a call. |
| `follow_up_sms_success_criteria` | Follow-up SMS success criteria | None | See [Follow-up SMS](#follow-up-sms). |

If the agent says "Enter your ID", the Digital Human always sends DTMF. If the agent says "What is your ID?", it uses `default_dtmf_or_voiced`.

</ParamField>

</ParamField>
<ParamField path="livekit_metadata" type="object">
  LiveKit configuration for this Digital Human.
</ParamField>

## Scripted responses

A scripted response makes a reply the same on each run. Each item pairs an agent line with a response.

| Field | Values | Notes |
|---|---|---|
| `match_phrase` | string | A line the agent says, for example "Can I have your account number?". A description of agent behavior never matches. |
| `match_type` | `exact`, `context` | `exact` is a fuzzy text comparison with no LLM call. `context` asks an LLM if the two lines mean the same thing. |
| `response_type` | `phrase`, `dtmf`, `silence`, `audio` | |
| `response_value` | string | Required for `phrase` and `dtmf`. Optional for `silence`. |
| `occurrence_mode` | `always`, `first_n` | |
| `occurrence_n` | integer above 0 | Required for `first_n`. |
| `silence_duration` | integer above 0 | Seconds of silence. |
| `scripted_response_audio_snippet_url` | string | The uploaded audio file for `audio`. |

If `scripted_responses_ordered` is `true`, the responses run in list order and each fires once. In this mode, an empty `match_phrase` fires on the next turn of the Digital Human.

## Follow-up SMS

Bluejay can grade the SMS that a voice agent sends after a call. The SMS shows under the call in the run results.

1. Set `follow_up_sms_sender_numbers` on the agent to the E.164 numbers that send the SMS. Use the API or the `update_agent` MCP tool.
2. Optional: set `follow_up_sms_success_criteria` on the Digital Human. If it is empty, Bluejay uses `success_criteria`.
3. Run the simulation.

Bluejay links an SMS to a call when all of these are true:

- The SMS goes to the phone number of the Digital Human.
- The sender is in `follow_up_sms_sender_numbers`.
- The SMS arrives within 30 minutes of the end of the call.
- The call completed. Calls that did not connect are not linked.

If more than one recent call used that number, Bluejay selects the call that matches the SMS content. Bluejay groups more than one SMS for the same call into one entry. If `follow_up_sms_sender_numbers` is empty, the feature is off.

## Best practices

### Write a Digital Human

- Test one goal in each Digital Human. Booking, rescheduling, and cancelling are three Digital Humans.
- Keep `intent` and `success_criteria` to one or two sentences each.
- Write `intent` as what the caller wants. If you write "correctly", "appropriately", or "successfully", move that text to `success_criteria`.
- Do not repeat in `intent` what a field sets. Bluejay already adds `traits`, `verbosity`, `fluency`, and end-of-call behavior to the prompt.
- Write `success_criteria` as an outcome of the agent that the transcript can show. Do not describe the actions of the Digital Human.
- Put grading that applies to every call in a [Custom Metric](/key-concepts/custom-metrics/overview), not in `success_criteria`.
- Set `test_name` to the scenario and use `tags` to group Digital Humans. `name` is the name the caller says.
- Ground the case in the agent context: the agent description, the synced [Workflow](/key-concepts/agents/overview#workflow), and the knowledge base. To check what Bluejay knows about the agent, ask Jay.

| Field | Do | Do not |
|---|---|---|
| `intent` | "You want to move your dentist appointment to next week." | "Make sure the agent correctly reschedules. If it asks for your date of birth, say March 3, 1980." |
| `success_criteria` | "The agent moved the appointment and confirmed the new date." | "The caller gives the date of birth and stays polite." |

### Make runs repeatable

Each "if the agent says X, the caller does Y" rule in `intent` is only a suggestion to the model. Move it to a field:

| Need | Field |
|---|---|
| A fixed value, for example a date of birth or order number | `traits` |
| A fixed line, keypad entry, or pause | `scripted_responses` |
| A fixed sequence of replies | `scripted_responses` with `scripted_responses_ordered` set to `true` |
| A fixed opening line | `speaks_first_config` |
| The same call on each run | `creativity` from 0.0 to 0.3 |

For exploratory and red team cases, keep `creativity` near the default of 0.7.

Before you create a batch, create one Digital Human, run it, and read the transcript. Bluejay accepts a configuration that has no effect, for example a scripted response that never matches.

To find regressions, run the same Digital Humans after each agent change. See [GitHub Actions](/cookbook/github-actions).

### Test patterns

| Test | Set |
|---|---|
| A fast caller | `voice_speed` to `fast` or `fastest` |
| A long pause in the call | A scripted response with `response_type` `silence` and a `silence_duration` |
| A bad line | `background_noise`, `audio_quality`, or `connection_quality` |
| A caller who talks over the agent | `interruptions` |
| Identity check before account data | A member ID in `traits`, and `success_criteria` such as "The agent verified the member ID before it gave the balance." |
| Each outcome of an outbound call | One Digital Human for each outcome, for example confirms, reschedules, or does not know about the appointment |
| A phone tree | [Scenario Builder](/key-concepts/scenario-builder/overview) |
