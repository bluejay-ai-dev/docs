Success criteria are the assertions on a Digital Human. Write them as discrete expected behaviors. Bluejay stores each bullet as a workspace **`success_criterion` metric**, grades it on every call, and exposes the checklist on `/v2`. Each conversation also gets one global **`success_score`** result: how many bullets passed, with `max_value` equal to how many bullets existed on that Digital Human when the call was graded.

`/v1` stays a string so existing integrations do not break.

## Author bullets, not a paragraph

Each bullet is one checkable behavior. A paragraph still grades — Bluejay wraps it as a single bullet — but a reviewer cannot see *which* behavior failed.

<Check>
Write one bullet per expected behavior:

- Agent greets the caller and confirms the account
- Agent states the required disclosure before collecting PII
- Agent offers a live transfer when the caller asks for a person
- Agent recaps next steps before hangup
</Check>

In the dashboard, add bullets on the Digital Human plus-list. On `/v1` create, update, and generate, send a newline-separated string. Bluejay mints one `success_criterion` metric per line and stores the current set as `[{id, text}]` on the Digital Human. Those metrics are **not** creatable in the Metrics library.

Use [custom metrics](/key-concepts/custom-metrics/overview) for a different dimension (tone, compliance, latency). Do not invent a library metric per success-criteria bullet.

## How a call is graded

Each current bullet is its own metric result (`boolean_value` + `reasoning`). The judge returns a verdict per id. The conversation also stores `success_score` as an integer count of passed bullets (`metadata.max_value` is the bullet count at grade time — not a percentage).

| Field | Meaning |
| --- | --- |
| `criteria[]` | Each current bullet with `id`, `text`, `passed`, `reasoning` |
| `criteria_pass_rate` | Share of current bullets that passed, `0`–`100`. Computed on read from those bullets. |
| `simulation_run.tests_passed` / `eval_failed` | A result passes when `success_score` equals `max_value` (every bullet passed). Anything else is a fail. |
| `simulation_run.success_rate` | Share of graded results that were 100% successful. Read from each conversation's `success_score` / `max_value`, same as the Outcome Success Rate column. |

A call that meets 3 of 4 behaviors stores `success_score` `3` with `max_value` `4`. That is **75** on the result and a **fail** in the run counts (`3 !== 4`). Reviewers override individual bullets with the existing per-metric human edit; the score is restamped.

Replacing the plus-list on update mints **new** metric rows and points the Digital Human at those ids. Previous `success_criterion` rows stay so historical `metric_results` keep their grades.

Goal widgets and pass-rate alerts average `success_criterion` results on the conversation. Older singleton Success rows (`f0f97934-…`) still count as one boolean 100 / 0. The builtin Success metric stays; `success_score` (`c2f1a8e4-…`) is the count analog.

## `/v1` vs `/v2`

The current set always lives as jsonb `[{id, text}]` on the test case. The HTTP version decides what the caller sees.

| Surface | `success_criteria` / grade |
| --- | --- |
| `/v1` digital human get, create, update, delete | Newline-joined **string** |
| `POST /v1/generate-digital-humans` | Writes bullets internally, returns a **string** |
| `GET /v1/retrieve-simulation-result(s)` | `goal_success` boolean only |
| `GET /v2/retrieve-simulation-results` | Run: `tests_passed` / `eval_failed` (100% rule) + `success_rate`. Each result: `criteria[]` + `criteria_pass_rate` |
| `GET /v2/retrieve-simulation-result` | `criteria[]` + `criteria_pass_rate` |
| `POST /v2/generate-digital-humans` | Returns `[{id, text}]` — this is the generate list. Do not put that list on `/v1`. |

<Note>
Generate already itemizes bullets in the database. The jsonb list on the **generate response** is a `/v2` field. `/v1/generate-digital-humans` will keep returning a string.
</Note>

```python
import os
import requests

BASE = "https://api.getbluejay.ai"
headers = {"X-API-Key": os.environ["BLUEJAY_API_KEY"]}

# v1 — same string contract as before
dh = requests.get(f"{BASE}/v1/get-digital-human/{dh_id}", headers=headers).json()
print(dh["success_criteria"])
# "Agent greets the caller\nAgent states the disclosure"

# v2 — graded checklist after a run
result = requests.get(
    f"{BASE}/v2/retrieve-simulation-result/{result_id}",
    headers=headers,
).json()["simulation_result"]
print(result["criteria_pass_rate"], result["criteria"])
```

## Where to read the checklist

- Conversation details in the app — each bullet with met / not met, plus per-bullet override
- [Retrieve Simulation Results v2](/api-reference/endpoint/retrieve-simulation-results-v2) and [Retrieve Simulation Result v2](/api-reference/endpoint/retrieve-simulation-result-v2)
- Goal widgets — average of `success_criterion` results (legacy singleton rows stay 100 / 0)

[Retrieve v1](/api-reference/endpoint/retrieve-simulation-results) is unchanged: `goal_success` is still pass/fail.
