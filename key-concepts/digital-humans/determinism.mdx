A Digital Human that improvises is testing the model's creativity instead of your agent. Every lever that removes improvisation is a field, and each field has exactly one job. The most common mistake, especially when building over the API or MCP, is writing behavior into the intent that a field already owns. The intent grows into a system prompt, the fields stay empty, and the call still drifts.

## One Field, One Job

<AccordionGroup>
  <Accordion title="Intent: the goal, in a sentence or two" icon="bullseye">
    The intent is a single slot in the Digital Human's system prompt, filled in at "here's the scenario you must enact". The template around it already renders the traits, the verbosity and fluency settings, a guardrail reminding the persona it is not the agent, and an end-of-call section. Anything you restate in the intent is duplicate prompt competing with the real thing.

    Write what the caller wants: `You are a member calling about your dental coverage to find out what your annual maximum is.` Stop there.
  </Accordion>
  <Accordion title="Traits: the fixtures the agent will ask for" icon="id-card">
    Member IDs, dates of birth, account numbers, order IDs, addresses. Traits render as their own labelled block in the prompt, so the persona has one place to look and you can swap a fixture without touching a word of the intent.

    A trait whose name looks like a phone number (`phone number`, `caller number`, `ANI`, `mobile`) overrides the Digital Human's own number when the agent asks for one. Name it accordingly and it does the right thing.
  </Accordion>
  <Accordion title="Scripted responses: the lines you need said verbatim" icon="list-check">
    When the exact wording matters, or when a keypad entry has to land on cue, put it in a scripted response rather than hoping the persona improvises it.
  </Accordion>
  <Accordion title="Speaks first: the opener on a silent line" icon="comment">
    A preset first message, for the case where the other end says nothing.
  </Accordion>
  <Accordion title="Creativity: how far the persona may wander" icon="dial">
    Model temperature. Drop it toward `0.2` for regression tests where you want the same call twice, and leave it near the default when you want coverage.
  </Accordion>
  <Accordion title="Hangup instructions: usually leave them alone" icon="phone-slash">
    The literal string `"default"` means built-in end-of-call behavior, which is tuned and handles the ordinary goodbyes. Any other string replaces it with your copy, so write one only when you need the call to end on a condition the default would miss.
  </Accordion>
</AccordionGroup>

## Scripted Responses

### A trigger is something the agent says

The `match_phrase` is matched against the agent's turn. With `exact` it is a fuzzy string comparison. With `context` an LLM is asked whether your phrase and the agent's turn mean the same thing, and it is told to be strict and to return nothing when unsure.

Either way the comparison is utterance against utterance, so the trigger has to read like a line the agent would actually speak.

<Check>
**A trigger:** `"Can I have your account number?"`. The agent might say this, or a paraphrase of it, and `context` will catch either.
</Check>

<Warning>
**Not a trigger:** `"The agent has finished answering and is inviting another question."`

This describes what the agent is doing. Nothing the agent says will ever mean the same thing as a stage direction, so the rule validates, saves, and never fires. Write the line you expect to hear instead: `"Is there anything else I can help you with today?"`
</Warning>

<Tip>
Reach for `exact` when you have the agent's literal line from a transcript. It is stricter and it skips an LLM call on every turn. Use `context` when you are matching an intent the agent could phrase several ways.
</Tip>

### Any order versus in order

Rules fire in one of two modes, and the mode changes what a repeated trigger means.

In **any order** (the default), every rule is live at once and whichever one's trigger comes up fires, subject to its occurrence limit. This is the mode for reactive fixtures: answer the ID question whenever it arrives, press 2 whenever the menu offers it.

In **in order**, the rules are a script. Only the first unfired step is armed. When the agent's turn releases it, it fires once and the next step arms. So the **same trigger repeated across several steps is correct, not a mistake**: each step fires on a successive occurrence of that line.

```json Four questions, asked one per closer
[
  { "match_type": "context", "match_phrase": "Thanks for calling. How can I help you today?",
    "response_type": "phrase", "response_value": "What does my dental cover?",
    "occurrence_mode": "always" },
  { "match_type": "context", "match_phrase": "Is there anything else I can help you with today?",
    "response_type": "phrase", "response_value": "How much is my annual maximum?",
    "occurrence_mode": "always" },
  { "match_type": "context", "match_phrase": "Is there anything else I can help you with today?",
    "response_type": "phrase", "response_value": "Is there a waiting period?",
    "occurrence_mode": "always" }
]
```

With `scripted_responses_ordered` set, that asks question one after the greeting and the next two on the first and second "anything else". Occurrence limits do not apply in this mode; every step fires exactly once, and once the script is exhausted the persona takes over.

### Blank triggers, and when they hurt

In **in order** mode a step with an empty `match_phrase` fires on the Digital Human's very next turn, whatever the agent said. That is the most deterministic thing the platform offers: no matching, no LLM, one line per turn.

It is also the wrong choice on any flow that verifies identity. A blank step fires when the agent asks for a date of birth, so the caller answers with the next line of the script instead of the date, and verification never completes. Use blank triggers for a fixed monologue like a voicemail, and named triggers when the agent will interrupt the script to ask you something.

## Speaks First

<Warning>
`dynamic` defaults to **true**, which waits up to five seconds for the agent to open and, if it does, yields the turn and **discards your custom message**. On any agent that greets callers, a preset opener configured this way is never heard.
</Warning>

That default is right for an inbound line: the agent greets, the caller replies. If you need the preset message spoken every time, set `dynamic` to false and accept that the Digital Human speaks at the top of the call, possibly over the greeting. If you want it only as a fallback for dead air, leave `dynamic` on and deliver the real opening line as the first step of a scripted response script instead.

## Before You Fan Out

Nothing in the API rejects a well-formed config that does nothing. A stage-direction trigger, a discarded speaks-first message, and a scripted response no agent turn will ever match all return `200`. Two habits catch the whole class:

<Steps>
  <Step title="Read a neighbor first">
    `GET /v1/digital-human/{id}` on an existing Digital Human in the same organization shows the conventions your team already settled on: how traits are named, whether callers enter an extension, what the tags mean. Cheaper than deriving it from a schema.
  </Step>
  <Step title="Dial one before you write eighty">
    Create a single Digital Human, run it, and read the transcript. A trigger that never fires is obvious in one call and invisible in a bulk create. Once it behaves, use the same shape for the batch.
  </Step>
</Steps>

<Tip>
Calibrate triggers against real transcripts rather than guesses. Before an agent is connected you do not know its greeting or its closer, so write the trigger you expect, run one call, and correct it from what the agent actually said.
</Tip>
