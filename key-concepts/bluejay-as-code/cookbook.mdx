Read the [pull → edit → push walkthrough](/key-concepts/bluejay-as-code/overview) first if you haven't already. This page picks up from there: which fields turn a Digital Human into a voicemail line, a customer journey, or a transcript replay, and the handful of field names Bluejay as Code renames from the API.

**Full field lists:** [create-digital-human](/api-reference/endpoint/create-digital-human), [add-agent](/api-reference/endpoint/add-agent), [create-custom-metric](/api-reference/endpoint/create-custom-metric).

## Field Names That Differ From the API

Bluejay as Code uses a few friendlier names in the payload than the underlying resource does:

| In your payload | API field | Entity |
|---|---|---|
| `description` | `intent` | Digital Human |
| `human_name` | `name` | Digital Human |
| `temperature` | `creativity` | Digital Human |

You can also set a Digital Human's voice with one combined key instead of three. `"accent": "en_american_masculine"` follows the pattern `language_accent_gender`, with gender spelled `masculine` or `feminine`. Bluejay splits it into `language`, `accent`, and `gender` on push. Pull always emits the three separate fields, so this shorthand only matters when you're hand-writing a new Digital Human.

## Choosing a Digital Human Type

A Digital Human's `tag` decides its type. The one exception is customer journeys, which use `journey_steps` instead. Pick one type per Digital Human. Each example below omits `simulations`; add it to attach the Digital Human to one, as shown on the [walkthrough](/key-concepts/bluejay-as-code/overview).

<AccordionGroup>
  <Accordion title="Base human">
    ```json
    {
      "bluejay_as_code_id": "a0e7b3d2-4c8f-4a91-b3e6-1d5f9c2e7a44",
      "human_name": "Maria Alvarez",
      "description": "New patient booking her first physical with Dr. Patel.",
      "success_criteria": "Agent books a Tuesday or Thursday morning slot with Dr. Patel."
    }
    ```
  </Accordion>

  <Accordion title="Voicemail">
    Set `tag` to `voicemail-custom` or `voicemail-ai-generated`.

    ```json
    {
      "bluejay_as_code_id": "9b3c7d5e-2a41-4a0f-8c6b-3e2d1f9a7c50",
      "human_name": "Voicemail Line",
      "tag": "voicemail-custom",
      "speaks_first_config": {
        "speaks_first": true,
        "mode": "custom",
        "message": "Hi, you've reached Maria. Leave a message after the tone."
      }
    }
    ```

    <Note>
      If `tag` carries more than one label, put the voicemail tag first. Bluejay only checks the first label.
    </Note>
  </Accordion>

  <Accordion title="Transcript replay">
    `formatted_transcript` replays a real call instead of `description`/`success_criteria`. `original_transcript` takes raw text instead and costs one LLM call to extract the turns.

    ```json
    {
      "bluejay_as_code_id": "6f1a9c3e-7b2d-4e11-9a5f-3c8d2b1e6a90",
      "human_name": "Replayed Caller",
      "formatted_transcript": [
        { "role": "caller", "utterance": "Hi, I need to reschedule my appointment." },
        { "role": "agent", "utterance": "Sure, what day works better for you?" },
        { "role": "caller", "utterance": "Could we do next Thursday afternoon?" }
      ]
    }
    ```
  </Accordion>

  <Accordion title="Customer journey">
    A [customer journey](/test/simulations/customer-journeys) runs multiple calls with the same caller in order.

    ```json
    {
      "bluejay_as_code_id": "d4f8a2c1-6b3e-4a09-8f27-1c5e9b0d3a76",
      "human_name": "Returning Caller",
      "journey_steps": [
        { "step": 1, "intent": "Book a Tuesday morning physical with Dr. Patel", "success_criteria": "Appointment booked and confirmation number read back" },
        { "step": 2, "intent": "Call back to confirm the appointment", "success_criteria": "Agent confirms the existing booking" }
      ]
    }
    ```
  </Accordion>

  <Accordion title="Scenario Builder">
    A Digital Human tagged `Scenario` is generated by [Scenario Builder](/key-concepts/scenario-builder/overview).

    ```json
    {
      "bluejay_as_code_id": "1f6c2e9a-4d3b-4a71-9c8e-7b0a2d1f6c94",
      "human_name": "Pharmacy Refill Caller",
      "tag": "Scenario",
      "workflow_v2_id": "64c79823-3d67-4648-874e-0a5de4c721bd",
      "workflow_path_index": 0,
      "enriched_playback": [
        { "turn": 1, "type": "message", "speaker": "user", "intent": "Caller wants to refill a prescription.", "exact_message": "Hi, I'm calling to refill my prescription." },
        { "turn": 2, "type": "message", "speaker": "agent", "criteria": "The agent verifies identity and confirms the prescription before proceeding.", "exact_match_text": "Sure, can I verify your name and date of birth first?" }
      ]
    }
    ```

    <Note>
      Don't write `enriched_playback` by hand. It won't stay in sync with the graph.
    </Note>
  </Accordion>

  <Accordion title="Red teaming">
    A Digital Human generated by a [red teaming](/key-concepts/red-teaming/overview) run carries `attack_vector`, `attack_type`, and a much larger `attack_plan`. Launch these through [red teaming](/key-concepts/red-teaming/launching-a-test), not Bluejay as Code.

    ```json
    {
      "bluejay_as_code_id": "8a3f1c7d-6e2b-4a90-b5d1-3c8f7a2e6b41",
      "human_name": "Verification Bypass Attempt",
      "attack_vector": "ambient_pretext",
      "attack_type": "audio_native"
    }
    ```
  </Accordion>
</AccordionGroup>

`livekit_metadata` is also a generated field: agent connection plumbing set through the agent's LiveKit connection settings, not written by hand.

## Agents, Simulations, and Custom Metrics

These three don't have archetypes the way Digital Humans do, so there's one example each instead of an accordion per variant.

### Agents

```json
{
  "bluejay_as_code_id": "f3d2a87c-1e4b-4b9a-9c2d-7f1e6b5a4c33",
  "name": "Front Desk Scheduler",
  "system_prompt": "You are the front desk scheduling agent for Cedar Park Family Medicine. Verify the caller's date of birth before discussing any patient-specific information. Help patients book, reschedule, or cancel appointments. Confirm provider, date, time, and reason for visit before finalizing.",
  "type": "INBOUND",
  "goals": [
    "Verify caller identity before discussing PHI",
    "Book, reschedule, or cancel the appointment",
    "Confirm provider, date, time, and reason for visit"
  ]
}
```

<Note>
  Every field here is exactly what [add-agent](/api-reference/endpoint/add-agent) takes.
</Note>

### Simulations

```json
{
  "bluejay_as_code_id": "b1a04e88-7c2f-4d23-9a5e-2f8c6d1b7a09",
  "name": "Scheduling Coverage",
  "description": "Booking, rescheduling, and cancellation paths for the front desk agent.",
  "max_concurrent": 5,
  "max_call_duration": 10,
  "max_call_duration_units": "minutes",
  "hangup_on_transfer": true
}
```

<Note>
  Every field here is exactly what [update-simulation](/api-reference/endpoint/update-simulation) takes. A simulation has no `agent` field of its own: a *new* simulation's owner comes from whichever agent's `simulations` array lists its `bluejay_as_code_id`, or from the bundle's only agent when there's just one. An existing simulation's owner can't be reassigned on push.
</Note>

### Custom Metrics

```json
{
  "bluejay_as_code_id": "2b8d4c1f-9a3e-4f72-b5c0-6e1d8a7f3c44",
  "name": "DOB Verified Before PHI",
  "prompt": "The agent verifies the caller's date of birth before discussing any patient-specific information.",
  "metric_type": "llm_judge",
  "eval_segment": "agent",
  "scope": "all",
  "response_type": "pass_fail"
}
```

<Note>
  Every field here is exactly what [create-custom-metric](/api-reference/endpoint/create-custom-metric) takes. `metric_type` decides which other fields apply — `tool_call` and the `audio_*` types read from `settings` instead of `prompt`.
</Note>

### Conditional and Composite Metrics

Two custom metric shapes live entirely in `settings`, so the [create-custom-metric](/api-reference/endpoint/create-custom-metric) field list doesn't show them. A conditional metric is any metric carrying `settings.fire_conditions`: it evaluates only on conversations that match, and comes back not applicable on the rest instead of failing them. A composite metric is `metric_type: "composite"`: it reads other metrics' scores and derives its own verdict arithmetically, with no LLM call of its own.

<AccordionGroup>
  <Accordion title="Gate a metric on a workflow node">
    `fire_conditions` is two levels. Conditions inside a group share that group's join, and the groups share the outer one. Both joins default to `and`, so a single gate needs nothing but `groups` and one condition. A condition's `type` is `workflow_node`, `tool_call`, or `metric`, taking `node_id`, `tool_name`, or a `metric_id` with an `operator` and a `value` respectively. Ten conditions is the ceiling across all groups.

    ```json
    {
      "bluejay_as_code_id": "bab41bd7-84d6-476b-b582-3957ad7b1dfe",
      "name": "Confirmation Read Back",
      "prompt": "Before ending the call, did the agent read the full reservation back to the caller and get an explicit confirmation?",
      "metric_type": "llm_judge",
      "response_type": "pass_fail",
      "settings": {
        "fire_conditions": {
          "groups": [
            {
              "conditions": [
                { "type": "workflow_node", "node_id": "node_2701krkx52cweknrbj75rbmapswf" }
              ]
            }
          ]
        }
      }
    }
    ```

    Read your agent's node ids with `GET /v1/agents/{agent_id}/workflow/summary`. Operators are `equals`, `not_equals`, `greater_than`, `less_than`, `greater_than_or_equal`, `less_than_or_equal`, `contains`, and `not_contains`.

    <Note>
      You may also see `settings.fire_node_ids`, a flat list of node ids. It still works so that metrics saved before conditions existed keep running, but it can't express joins or the other two condition types. Write `fire_conditions` instead.
    </Note>
  </Accordion>

  <Accordion title="Derive a number from other metrics">
    A quantitative composite declares the metrics it reads in `variables` and combines them in one `master_formula`. A metric is referenced by its id in double quotes, which is the only way to name one, so the formula survives a rename. The grammar is arithmetic only — `+ - * / % **` plus `min`, `max`, `abs`, `round`, `floor`, and `ceil`. A variable whose metric isn't already a number carries a `value_map` turning each of its outcomes into one.

    ```json
    {
      "bluejay_as_code_id": "373c5941-90cb-4818-bf5d-a8962cd1beda",
      "name": "Reservation Quality Score",
      "prompt": "Weighted 1-5 score: 60% booking clarity, 40% whether every reservation detail was captured.",
      "metric_type": "composite",
      "response_type": "quantitative",
      "min_value": 1,
      "max_value": 5,
      "settings": {
        "composite": {
          "output_type": "quantitative",
          "variables": [
            { "metric_id": "a8c007f9-390d-4d34-9e13-a72a4ad8aed9" },
            {
              "metric_id": "af9bd0ed-67b2-4148-9d64-82b2e1a4e325",
              "value_map": { "pass": 5, "fail": 1 }
            }
          ],
          "master_formula": "round(\"a8c007f9-390d-4d34-9e13-a72a4ad8aed9\" * 0.6 + \"af9bd0ed-67b2-4148-9d64-82b2e1a4e325\" * 0.4)"
        }
      }
    }
    ```

    The stored result keeps its own arithmetic in `reasoning`, so a derived number stays auditable after the fact.
  </Accordion>

  <Accordion title="Derive a label from other metrics">
    A categorical composite swaps the formula for `rules`. Each rule names an `output` and the `conditions` that produce it, in the same two-level shape as `fire_conditions` but comparing declared metrics against numbers. Rules are evaluated in order and the first one that holds wins, so put the strictest first. If none hold the metric is not applicable rather than falling back to a default label. Ten rules, and ten conditions per rule, are the ceilings.

    ```json
    {
      "bluejay_as_code_id": "924ba13f-037d-4f34-af93-53b072168ea6",
      "name": "Reservation Outcome Grade",
      "metric_type": "composite",
      "response_type": "enum",
      "enum_options": ["Clean", "Usable", "Poor"],
      "settings": {
        "composite": {
          "output_type": "categorical",
          "variables": [
            { "metric_id": "a8c007f9-390d-4d34-9e13-a72a4ad8aed9" },
            {
              "metric_id": "af9bd0ed-67b2-4148-9d64-82b2e1a4e325",
              "value_map": { "pass": 1, "fail": 0 }
            }
          ],
          "rules": [
            {
              "output": "Clean",
              "conditions": {
                "groups": [
                  {
                    "join": "and",
                    "conditions": [
                      { "metric_id": "a8c007f9-390d-4d34-9e13-a72a4ad8aed9", "operator": "greater_than_or_equal", "value": 4 },
                      { "metric_id": "af9bd0ed-67b2-4148-9d64-82b2e1a4e325", "operator": "equals", "value": 1 }
                    ]
                  }
                ]
              }
            },
            {
              "output": "Poor",
              "conditions": {
                "groups": [
                  {
                    "join": "or",
                    "conditions": [
                      { "metric_id": "a8c007f9-390d-4d34-9e13-a72a4ad8aed9", "operator": "less_than", "value": 3 },
                      { "metric_id": "af9bd0ed-67b2-4148-9d64-82b2e1a4e325", "operator": "equals", "value": 0 }
                    ]
                  }
                ]
              }
            }
          ]
        }
      }
    }
    ```

    A rule can only read a metric that variables already declares.
  </Accordion>
</AccordionGroup>

<Warning>
  Metrics that read other metrics stay one level deep. A conditional metric may produce no result at all, so nothing can be built on top of one: a fire condition or a composite variable pointing at a conditional metric is refused with `422`, and so is turning a metric that other metrics already read into a conditional or composite one. Reference a metric that always evaluates instead.
</Warning>

Shape errors are quieter than that. A bad `output_type`, or a formula reading a metric `variables` never declared, comes back `200` with `valid: false` and an errors array, because push checks the payload before it reaches the create call. Read `valid` on every push rather than the status code alone.

### Wiring them together

A simulation's `digital_humans`, an agent's `custom_metrics`, and a custom metric's `agents` are all desired-state arrays, not append-only lists. Push replaces each one with exactly what you listed. Drop an id that was there before, and Bluejay unlinks it without deleting the object itself. See [reconciliation](/key-concepts/bluejay-as-code/overview) in the walkthrough for the full behavior.
