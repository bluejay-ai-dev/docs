Every entity in a BaC payload takes the same fields as its corresponding API resource. See the [pull → edit → push walkthrough](/key-concepts/bluejay-as-code/overview) for the flow itself, and the [create-digital-human](/api-reference/endpoint/create-digital-human), [add-agent](/api-reference/endpoint/add-agent), and [create-custom-metric](/api-reference/endpoint/create-custom-metric) references for the full field lists. This page covers what those references don't: which field combination gives you which digital human behavior, where BaC's field names differ from the API's, and where the pull/push round-trip has gaps.

## Field names that differ from the API

BaC uses a few friendlier names in the payload than the underlying resource does:

| In your BaC file | API field | Entity |
|---|---|---|
| `description` | `intent` | Digital human |
| `human_name` | `name` | Digital human |
| `temperature` | `creativity` | Digital human |
| `agent_description` | `system_prompt` | Agent |

You can also set a digital human's voice with one combined key instead of three. `"accent": "en_american_masculine"` follows the pattern `language_accent_gender`, with gender spelled `masculine` or `feminine`. Bluejay splits it into `language`, `accent`, and `gender` on push. Pull always emits the three separate fields, so this shorthand only matters when you're hand-writing a new digital human.

## Choosing a digital human type

A digital human's `tag` decides which fields are required and which are forbidden. For journeys, `journey_steps` decides it instead. Pick one archetype per digital human; mixing them isn't supported.

<AccordionGroup>
  <Accordion title="Plain call">
    No tag. `description` (intent) is required.

    ```json
    {
      "bluejay_as_code_id": "a0e7b3d2-4c8f-4a91-b3e6-1d5f9c2e7a44",
      "human_name": "Maria Alvarez",
      "description": "New patient booking her first physical with Dr. Patel.",
      "success_criteria": "Agent books a Tuesday or Thursday morning slot with Dr. Patel.",
      "simulations": ["b1a04e88-7c2f-4d23-9a5e-2f8c6d1b7a09"]
    }
    ```
  </Accordion>

  <Accordion title="Customer journey">
    A journey runs multiple calls with the same caller, in order. Set `journey_steps` instead of `description`. No tag is needed; Bluejay applies `"Customer Journey"` automatically. Step numbers start at 1 and must be contiguous, and every step needs its own `intent`. Full rules are in the [walkthrough](/key-concepts/bluejay-as-code/overview).

    ```json
    {
      "bluejay_as_code_id": "d4f8a2c1-6b3e-4a09-8f27-1c5e9b0d3a76",
      "human_name": "Returning Caller",
      "simulations": ["b1a04e88-7c2f-4d23-9a5e-2f8c6d1b7a09"],
      "journey_steps": [
        { "step": 1, "intent": "Book a Tuesday morning physical with Dr. Patel", "success_criteria": "Appointment booked and confirmation number read back" },
        { "step": 2, "intent": "Call back to confirm the appointment", "success_criteria": "Agent confirms the existing booking" }
      ]
    }
    ```
  </Accordion>

  <Accordion title="Voicemail">
    Set `tag` to `voicemail-custom` or `voicemail-ai-generated`. Neither `description` nor `success_criteria` is needed. Full recipe in the [walkthrough](/key-concepts/bluejay-as-code/overview).

    ```json
    {
      "bluejay_as_code_id": "9b3c7d5e-2a41-4a0f-8c6b-3e2d1f9a7c50",
      "human_name": "Voicemail Line",
      "tag": "voicemail-custom",
      "speaks_first_config": {
        "speaks_first": true,
        "mode": "custom",
        "message": "Hi, you've reached Maria. Leave a message after the tone."
      },
      "simulations": ["b1a04e88-7c2f-4d23-9a5e-2f8c6d1b7a09"]
    }
    ```

    If `tag` carries more than one label, put the voicemail sentinel first. Bluejay only checks the first label.
  </Accordion>

  <Accordion title="Transcript replay">
    Give Bluejay a real call transcript instead of writing `description` and `success_criteria` yourself. `formatted_transcript` takes a pre-structured `[{role, utterance}]` list, shown below. `original_transcript` takes raw text instead; Bluejay runs one LLM call to extract the turns and derive intent from it.

    ```json
    {
      "bluejay_as_code_id": "6f1a9c3e-7b2d-4e11-9a5f-3c8d2b1e6a90",
      "human_name": "Replayed Caller",
      "formatted_transcript": [
        { "role": "caller", "utterance": "Hi, I need to reschedule my appointment." },
        { "role": "agent", "utterance": "Sure, what day works better for you?" },
        { "role": "caller", "utterance": "Could we do next Thursday afternoon?" }
      ],
      "simulations": ["b1a04e88-7c2f-4d23-9a5e-2f8c6d1b7a09"]
    }
    ```
  </Accordion>

  <Accordion title="Scenario Builder graph">
    Don't hand-author this one. A digital human tagged `scenario` is the compiled output of a Scenario Builder graph. Bluejay writes its `enriched_playback` and keeps it synced whenever you edit the graph. Build these through [Scenario Builder](/key-concepts/scenario-builder/overview) and `generate-digital-humans` instead. A hand-written `enriched_playback` won't stay in sync with anything.
  </Accordion>
</AccordionGroup>

<Warning>
  A few more digital-human fields exist on the model, and BaC's push won't reject them, but Bluejay writes them itself as the output of another feature. `workflow_v2_id`, `workflow_path_index`, and `tested_path` link a digital human back to the Scenario Builder graph it came from. `attack_vector`, `attack_type`, and `attack_plan` come from the [red teaming](/key-concepts/red-teaming/overview) launch flow. `livekit_metadata` is agent connection plumbing. Setting any of these by hand can produce a digital human in a state the UI never creates.
</Warning>

## What doesn't round-trip on pull

Pulling a digital human doesn't return everything push accepts. `traits`, `scripted_responses`, `expected_tool_calls`, `custom_voice_id`, `extension`, `original_transcript`, `formatted_transcript`, `num_runs`, and the generated fields listed above are written on push but never come back on pull. If a digital human has any of these set, a pull, edit, push cycle silently drops them. Keep those fields in your own source file instead of trusting pull to preserve them. Agents and simulations don't have this gap. Their pull round-trips everything.

## Agents, simulations, and custom metrics

These three don't have archetypes the way digital humans do. Every field beyond the renames above works exactly as documented on their API pages. One thing worth knowing: `digital_humans` on a simulation, and `custom_metrics` or `agents` on an agent or metric, are desired-state arrays, not append-only. See [reconciliation](/key-concepts/bluejay-as-code/overview) in the walkthrough for what happens when you omit an id that was there before.
