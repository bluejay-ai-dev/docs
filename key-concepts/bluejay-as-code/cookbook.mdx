Every entity in a BaC payload takes the same fields as its corresponding API resource (see the [pull → edit → push walkthrough](/key-concepts/bluejay-as-code/overview) and the [create-digital-human](/api-reference/endpoint/create-digital-human), [add-agent](/api-reference/endpoint/add-agent), and [create-custom-metric](/api-reference/endpoint/create-custom-metric) references for the full field lists). This page covers what those references don't: which field combination gives you which digital human behavior, where BaC's field names differ from the API's, and where the pull/push round-trip has gaps.

## Field names that differ from the API

BaC uses a few friendlier names in the payload than the underlying resource does:

| In your BaC file | API field | Entity |
|---|---|---|
| `description` | `intent` | Digital human |
| `human_name` | `name` | Digital human |
| `temperature` | `creativity` | Digital human |
| `agent_description` | `system_prompt` | Agent |

You can also set a digital human's voice with one combined key instead of three: `"accent": "en_american_masculine"` (`language_accent_gender`, gender spelled `masculine`/`feminine`) splits into `language`, `accent`, and `gender` on push. Pull always emits the three separate fields, so this shorthand only comes up when you're hand-writing a new digital human.

## Choosing a digital human type

A digital human's `tag` (and, for journeys, `journey_steps`) decides which fields are required and which are forbidden. Pick one — mixing archetypes on the same digital human isn't supported.

<AccordionGroup>
  <Accordion title="Plain call">
    No tag. `description` (intent) is required.

    ```json
    {
      "bluejay_as_code_id": "a0e7b3d2-4c8f-4a91-b3e6-1d5f9c2e7a44",
      "human_name": "Maria Alvarez",
      "description": "New patient booking her first physical with Dr. Patel.",
      "success_criteria": "Agent books a Tuesday or Thursday morning slot with Dr. Patel.",
      "simulations": ["b1a04e88-7c2f-4d23-9a5e-2f8c6d1b7a09"]
    }
    ```
  </Accordion>

  <Accordion title="Customer journey (multi-call)">
    Set `journey_steps` instead of `description` — no tag needed, Bluejay auto-applies `"Customer Journey"`. Full step rules (1-based numbering, contiguous, per-step `intent` required) are in the [walkthrough](/key-concepts/bluejay-as-code/overview).

    ```json
    {
      "bluejay_as_code_id": "d4f8a2c1-6b3e-4a09-8f27-1c5e9b0d3a76",
      "human_name": "Returning Caller",
      "simulations": ["b1a04e88-7c2f-4d23-9a5e-2f8c6d1b7a09"],
      "journey_steps": [
        { "step": 1, "intent": "Book a Tuesday morning physical with Dr. Patel", "success_criteria": "Appointment booked and confirmation number read back" },
        { "step": 2, "intent": "Call back to confirm the appointment", "success_criteria": "Agent confirms the existing booking" }
      ]
    }
    ```
  </Accordion>

  <Accordion title="Voicemail">
    `tag` must be `voicemail-custom` or `voicemail-ai-generated` — no `description`/`success_criteria` needed. Full recipe in the [walkthrough](/key-concepts/bluejay-as-code/overview).

    ```json
    {
      "bluejay_as_code_id": "9b3c7d5e-2a41-4a0f-8c6b-3e2d1f9a7c50",
      "human_name": "Voicemail Line",
      "tag": "voicemail-custom",
      "speaks_first_config": {
        "speaks_first": true,
        "mode": "custom",
        "message": "Hi, you've reached Maria. Leave a message after the tone."
      },
      "simulations": ["b1a04e88-7c2f-4d23-9a5e-2f8c6d1b7a09"]
    }
    ```

    If `tag` carries more than one label, put the voicemail sentinel first — Bluejay only checks the first one.
  </Accordion>

  <Accordion title="Transcript replay">
    Hand Bluejay a real call transcript instead of writing `description`/`success_criteria` yourself. `formatted_transcript` (shown below) skips straight to a `[{role, utterance}]` list; `original_transcript` takes raw text instead and costs one LLM call to extract the turns and derive intent.

    ```json
    {
      "bluejay_as_code_id": "6f1a9c3e-7b2d-4e11-9a5f-3c8d2b1e6a90",
      "human_name": "Replayed Caller",
      "formatted_transcript": [
        { "role": "caller", "utterance": "Hi, I need to reschedule my appointment." },
        { "role": "agent", "utterance": "Sure, what day works better for you?" },
        { "role": "caller", "utterance": "Could we do next Thursday afternoon?" }
      ],
      "simulations": ["b1a04e88-7c2f-4d23-9a5e-2f8c6d1b7a09"]
    }
    ```
  </Accordion>

  <Accordion title="Scenario Builder graph (don't hand-author)">
    A `scenario`-tagged digital human is the compiled output of a Scenario Builder graph — Bluejay writes its `enriched_playback` and keeps it synced whenever you edit the graph. Build these through [Scenario Builder](/key-concepts/scenario-builder/overview) and `generate-digital-humans`, not by writing `enriched_playback` yourself; a hand-written one won't stay in sync with anything.
  </Accordion>
</AccordionGroup>

<Warning>
  A few more digital-human fields exist on the model and BaC's push won't reject them, but Bluejay writes them as output of another feature: `workflow_v2_id`, `workflow_path_index`, and `tested_path` (Scenario Builder's link back to its source graph), `attack_vector`/`attack_type`/`attack_plan` (the [red teaming](/key-concepts/red-teaming/overview) launch flow), and `livekit_metadata` (agent connection plumbing). Setting these by hand can produce a digital human in a state the UI never creates.
</Warning>

## What doesn't round-trip on pull

Pulling a digital human doesn't return everything push accepts. `traits`, `scripted_responses`, `expected_tool_calls`, `custom_voice_id`, `extension`, `original_transcript`, `formatted_transcript`, `num_runs`, and the generated fields listed above are written on push but never come back on pull. If a digital human has any of these set, a pull → edit → push cycle silently drops them — keep those fields in your own source file rather than trusting pull to preserve them. Agents and simulations don't have this gap; their pull round-trips everything.

## Agents, simulations, and custom metrics

These three don't have archetypes the way digital humans do — every field beyond the renames above works exactly as documented on their API pages. The one thing worth knowing: `digital_humans` on a simulation and `custom_metrics`/`agents` on an agent or metric are desired-state arrays, not append-only — see [reconciliation](/key-concepts/bluejay-as-code/overview) in the walkthrough for what happens when you omit an id that was there before.
