## Create a Custom Metric

A metric runs on the conversations of the agents you connect it to. A simulation can limit a run to selected metrics. To test a metric against labeled conversations before you use it, use the [Metrics Lab](/key-concepts/metrics-lab/overview).

To put call-specific values into the prompt, use [dynamic variables](/key-concepts/custom-metrics/prompting-guide#dynamic-variables).

## Metric types

| Type (UI label) | `metric_type` | How it scores |
|---|---|---|
| LLM as a Judge | `llm_judge` | An LLM scores the conversation against your prompt. |
| Composite | `composite` | Combines the results of other metrics into one score or label. |
| Tool Call | `tool_call` | Passes when the agent called the tools you name. |
| Phrase Match | `transcript_regex` | Checks whether specific words were said. |
| Transfer Landed | `transfer_landed` | Passes when the Digital Human in `settings.receiver_test_case_id` answers a transfer from the agent within `settings.window_seconds` (default 180, maximum 900). |

Tool Call, Phrase Match, and Transfer Landed always return Pass/Fail. Only `llm_judge` uses `prompt`. The other types read `settings`.

## Response types

The response type sets the shape of an LLM as a Judge result.

| Response type (UI label) | `response_type` | Example |
|---|---|---|
| Pass/Fail | `pass_fail` | Did the agent verify identity before it shared account details? |
| Yes/No | `yes_no` | Did the customer ask for a human? |
| Number | `quantitative` | Rate the clarity of the explanation from 1 to 5. |
| Text | `qualitative` | Summarize the objections the customer raised. |
| Categorical | `enum` | Classify the call as `resolved`, `escalated`, or `unresolved`. |
| Structured JSON | `json` | Return `identity_verified` (boolean) and `flags` (string array). |

Text results do not roll up into a number. If you need a trend, add a Pass/Fail or Number metric next to the Text metric.

## Composite metrics

A composite or conditional metric can read only plain metrics. It cannot use another composite or conditional metric as an input or a condition.

A composite metric reads the results of other metrics on the same conversation. It makes no LLM call.

- List the input metrics in `settings.composite.variables`. A metric whose result is not a number needs a `value_map`, for example `{ "pass": 5, "fail": 1 }`.
- For a number, set `output_type` to `quantitative` and write a `master_formula`. The formula names a metric by its ID in double quotes, for example `round(100 * ("<metric_id>" / 5))`.
- Formula operators are `+`, `-`, `*`, `/`, `%`, and `**`. Functions are `min`, `max`, `abs`, `round`, `floor`, and `ceil`.
- For a label, set `output_type` to `categorical`, set `response_type` to `enum`, and write `rules`. Bluejay checks the rules in order and uses the first match. If no rule matches, the result is Not Applicable.
- You can use 10 rules maximum, with 10 conditions maximum each. A rule can read only a metric that `variables` lists.

## Conditional metrics

A conditional metric runs only on conversations that match its conditions. On other conversations, its result is Not Applicable. A condition can check that:

- The conversation reached a node of the agent [Workflow](/key-concepts/agents/overview#workflow). To find node IDs, use [Get Workflow Summary](/api-reference/endpoint/get-workflow-summary).
- The agent called a given tool.
- Another metric has a given result, for example Fail.

Join conditions with "and" or "or", up to 10 conditions for each metric. The [conditional metric example](/key-concepts/bluejay-as-code/cookbook#conditional-metrics) shows the JSON.

## Tool calls, events, and metadata

Send tool calls, events, and metadata with a conversation so metrics can check what the agent did, not only what it said. For example, a metric can check that the agent looked up the order before it gave a delivery date.

### Send tool calls

<Tabs>
  <Tab title="Simulations">
    Bluejay sends an `X-Simulation-Result-Id` with each simulated call. Your agent reads it, records its tool calls during the call, and sends them after the call ends.

    | Connection | Where the ID arrives |
    |------------|----------------------|
    | [SIP](/simulation-integrations/sip) | A custom header on the SIP INVITE. |
    | [WebSocket](/simulation-integrations/websockets) | A header on the WebSocket upgrade request. |

    The phone network usually drops custom headers, so a Phone connection cannot pass the ID. Use SIP for phone agents. For a voice platform or framework, its integration page says where the ID arrives.

    After the call ends, send the data to [`POST /v1/update-simulation-result`](/api-reference/endpoint/update-simulation-result):

    ```json
    {
      "simulation_result_id": "1234",
      "tool_calls": [
        {
          "name": "transfer_funds",
          "parameters": { "from": "12345", "to": "67890", "amount": 500 },
          "output": { "transaction_id": "txn_abc123", "status": "completed" },
          "start_offset_ms": 120000
        }
      ],
      "events": [
        { "title": "Customer verified", "start_offset_ms": 30000, "tags": ["verification"] }
      ],
      "metadata": { "resolution_status": "resolved" }
    }
    ```

    Some integrations collect tool calls without this API call. The integration page for your platform says if it does.
  </Tab>
  <Tab title="Production">
    Put `tool_calls`, `events`, and `metadata` in the same [`POST /v1/evaluate`](/api-reference/endpoint/evaluate) request as the transcript or recording. You cannot add them later.

    ```json
    {
      "agent_id": "123",
      "start_time_utc": "2026-07-16T18:00:00Z",
      "participants": [
        { "role": "AGENT", "spoke_first": true },
        { "role": "USER", "spoke_first": false }
      ],
      "recording_url": "https://storage.example.com/call.mp3",
      "tool_calls": [
        {
          "name": "check_order_status",
          "start_offset_ms": 2000,
          "description": "Look up order status by order ID",
          "parameters": { "order_id": "ORD-2024-001" },
          "output": { "status": "in_transit" }
        }
      ],
      "metadata": { "customer_tier": "premium" }
    }
    ```
  </Tab>
</Tabs>

### Tool call fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | Yes | The tool name. |
| `start_offset_ms` | integer | Yes | Milliseconds from the start of the conversation. |
| `description` | string | No | What the tool does. Custom Metrics read it. |
| `parameters` | object | No | The input to the tool. |
| `output` | any | No | The value the tool returned. |

### Event fields

An event marks a moment in the conversation, for example an escalation or a hold.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `title` | string | Yes | The event name. |
| `start_offset_ms` | integer | Yes | Milliseconds from the start of the conversation. |
| `end_offset_ms` | integer | No | When the event ended. |
| `description` | string | No | Details of the event. |
| `tags` | string[] | No | Tags for the event. |
| `metadata` | object | No | Extra data for the event. |

### Metadata

`metadata` is a free-form JSON object for the whole conversation. Bluejay puts each key into the matching `{{placeholder}}` in your Custom Metrics. See [dynamic variables](/key-concepts/custom-metrics/prompting-guide#dynamic-variables).
